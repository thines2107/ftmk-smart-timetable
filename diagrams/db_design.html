Database Normalization
Applied normalization rules from 1NF to 3NF

Normalization is the process of organizing a relational database to reduce data redundancy and improve data integrity. The FTMK Smart Timetable Arrangement System database has been normalized to the Third Normal Form (3NF). The following describes how each form has been applied.

First Normal Form (1NF) — Atomic Values, No Repeating Groups

Rule: Each column must contain only atomic (indivisible) values. No repeating groups or arrays are allowed in a single column.

  • Every attribute across all 5 tables holds a single, atomic value. For example, start_time and end_time are stored as separate TIME columns in the timetable table — not combined into one string.
  • Multiple class sessions for a subject are stored as separate rows in timetable, not as comma-separated values in one field.
  • A student who saves multiple timetables has multiple rows in saved_timetables, not one row with multiple values.

Result: All tables satisfy 1NF. ✓

Second Normal Form (2NF) — No Partial Dependency

Rule: The table must be in 1NF, and all non-key attributes must be fully functionally dependent on the entire primary key (applies to composite keys).

  • All tables in the system use a single-column surrogate primary key (id, SERIAL/AUTO_INCREMENT). Since there are no composite primary keys, partial dependencies cannot exist by definition.
  • For example, in timetable, all attributes (subject_name, day, start_time, room, etc.) are fully dependent on the single id primary key.
  • In saved_timetables, name, data, and is_primary are all fully dependent on id.

Result: All tables satisfy 2NF. ✓

Third Normal Form (3NF) — No Transitive Dependency

Rule: The table must be in 2NF, and no non-key attribute may depend on another non-key attribute (no transitive dependencies).

  • Lecturer details (email, department, block, office_room) are stored in the separate lecturer_profiles table rather than repeating them in every row of the timetable table. This eliminates the transitive dependency: id → lecturer_name → email/department/office.
  • Student academic profile information (year, course, group_name) belongs to the users table and is not repeated in saved_timetables. The foreign key user_id is used to join when needed.
  • Friend names are stored in saved_friends.friend_name as a snapshot at the time of adding, intentionally decoupled from users.name to avoid dependency on a non-key attribute of another table.

Result: All tables satisfy 3NF. ✓

Note — Intentional Denormalization in saved_timetables.data

The data column in saved_timetables stores a complete JSON snapshot of the student's chosen timetable combination. This is a deliberate and justified deviation from strict normalization:

  • If timetable master records are later updated or deleted by the admin, the student's saved choice must remain intact and unchanged.
  • Storing a JSON snapshot ensures historical data integrity — the saved timetable always reflects what the student chose, regardless of future changes to the master timetable table.
  • This pattern is widely accepted in production systems as a deliberate denormalization for audit and snapshot purposes.
